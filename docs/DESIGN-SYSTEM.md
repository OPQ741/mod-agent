### 1.2 架构决策记录（ADR 摘要）

| # | 决策 | 理由 |
| --- | --- | --- |
| **ADR-1** | 单 Agent 主循环 + 受控子任务派生，不做对等 Multi-Agent 编排 | 单循环可解释、可恢复、成本可控 |
| **ADR-2** | 扁平消息日志为唯一事实源（Source of Truth） | 匹配无状态回放、最大化 prompt cache、简化调试 |
| **ADR-3** | 结构化专用工具为主、通用 Shell 为辅 | 结构化工具返回确定性输出；Shell 保留给构建/测试 |
| **ADR-4** | 混合检索（词法+符号+语义+依赖图），不纯靠向量 RAG | 编码任务锚定精确标识符，纯语义召回不足 |
| **ADR-5** | Task State 外置持久化（TASK_STATE 文件） | 对抗目标漂移，压缩/重启后不丢失 |
| **ADR-6** | LLM 网关统一封装（多模型路由/缓存/限流/重试） | 隔离 provider 差异，成本/质量关键杠杆 |

### 1.3 核心数据模型

```python
class Message:                       # 扁平日志最小单元
    role: "system"|"user"|"assistant"|"tool_result"
    content: str | list[ContentBlock]   # text / image / tool_call
    tool_call_id: str | None
    token_count: int                    # 预算管理
    created_at: datetime

class ToolCall:
    id: str
    name: str                  # read_file / edit_file / run_command ...
    arguments: dict            # JSON Schema 校验后
    requires_approval: bool

class TaskState:               # 外置持久化，对抗目标漂移
    task_id: str
    original_request: str          # 原始需求，永不被改写
    clarified_requirements: list[str]
    constraints: list[str]
    plan: list[PlanStep]
    acceptance_criteria: list[str] # 尽可能转可执行测试
    attempted_fixes: list[FixRecord]
    status: "planning"|"executing"|"verifying"|"done"|"blocked"
    checkpoints: list[Checkpoint]  # 消息日志快照

class ContextBudget:           # 128K 窗口典型分配
    system_prompt_and_tools: 5_000
    task_definition:        2_000
    recent_history:        10_000
    retrieved_code:        80_000    # 大头
    working_memory:        20_000
    response_buffer:       11_000
```

## 2. 核心模块设计

模块分两组：架构图上层的**四个功能模块**（直接产出任务价值）与 Agent Loop 之下的**四个运行时支撑模块**（保障循环可靠运行）。

### 2.1 功能模块（四件套）

- **需求解析与任务规划**：意图分类、歧义检测、澄清问题生成（AskUser）、验收标准转可执行测试、多步计划生成；输出 `TaskState` 初稿（含原始需求、约束、验收标准）。对应 Phase 2。
- **代码生成与修改**：基于检索上下文生成/编辑代码；以结构化专用工具（read/edit/write）为主，版本校验防并发冲突；以可审查 diff 呈现变更。
- **执行反馈与自我修正**：驱动「改文件→跑测试→修复」工具循环；按错误类型路由（见 4 章 C3）；管理迭代预算与人工升级。
- **完成判定与交付**：对照 `acceptance_criteria` 判定 `done`；生成变更摘要 + diff；触发记忆沉淀（AGENT.md 更新）。

### 2.2 运行时支撑模块

| 模块 | 职责 | 关键设计点 |
| --- | --- | --- |
| **上下文组装器** | 每轮拼装 TaskState+检索+记忆+历史，做预算裁剪 | progressive disclosure 按需加载；按 `ContextBudget` 分配；使用率 >90% 触发 compaction |
| **工具引擎** | 执行工具调用、沙箱隔离、结果规整截断 | 结构化工具为主、shell 为辅（ADR-3）；JSON Schema 校验入参；超时/隔离保护 |
| **状态存储** | 消息日志(JSONL) + TaskState 持久化 + 索引 | 扁平日志为唯一事实源（ADR-2）；TaskState 外置（ADR-5）；checkpoints 检查点 |
| **权限与安全** | 危险操作拦截、授权确认 | P5 安全默认；权限分级；破坏性操作（删除/覆盖/force push）显式确认 |

## 3. 关键交互与数据流转

### 3.1 端到端任务生命周期（以「加账户注销接口」为例）

```
用户        UI/CLI        Agent Loop        工具/沙箱      状态存储
 │ "加注销    │               │                 │             │
 │  接口"     │─解析请求─▶     │                 │             │
 │           │               │─意图/歧义检测─▶   │             │
 │           │               │─search_codebase▶│ 混合检索     │
 │           │               │◀─相关文件/符号─  │             │
 │ ◀澄清──── │◀─AskUser────── │                 │             │
 │ "不允许" ─▶│─────────────▶ │                 │             │
 │           │               │─计划+验收测试─▶  │─TaskState─▶  │
 │ "开始" ──▶│─────────────▶ │                 │             │
 │           │              ==子循环:编辑==     │             │
 │           │               │─edit(版本校验)▶ │─日志追加─▶    │
 │           │               │─run_tests────▶  │ 沙箱         │
 │           │               │◀─2断言失败──     │             │
 │           │              ==修复循环==        │─失败记录─▶    │
 │           │               │◀─全部通过──      │             │
 │ ◀diff审查─│◀─摘要+diff─── │                 │             │
 │ "接受" ──▶│─────────────▶ │─归档+记忆沉淀─▶  │─AGENT.md─▶   │
```

### 3.2 单轮数据流全景

```
                 ┌────────── 持久层 ──────────┐
                 │ 会话日志(JSONL) TaskState   │
                 │ RepoMap/向量/符号  AGENT.md │
                 └──────▲──────────▲──────────┘
          每轮写入 ◀─────┘          └─────▶ 每轮读取
 ┌──────────────────────┴──────────┴──────────────────┐
 │  Agent Loop 单轮：                                  │
 │  TaskState+检索+记忆+历史 → [Context Assembler]      │
 │   ─预算裁剪→ 消息列表 → LLM 网关                     │
 │   ←解析输出(文本|工具调用) ← [Security Gate]         │
 │   → 工具引擎(沙箱) → 结构化结果 → 追加消息日志        │
 │   └─使用率>90%? → [Compaction] → 下一轮             │
 └────────────────────────────────────────────────────┘
```

### 3.3 三类场景流程差异

| 阶段 | 新功能开发 | Bug 修复 | 代码库问答 |
| --- | --- | --- | --- |
| 需求解析 | 澄清决策→验收测试 | issue→复现→失败用例 | 直接检索 |
| 计划 | 多步（接口/实现/测试） | 假设驱动定位 | 无，纯检索 |
| 执行 | 生成+编辑+测试 | 复现→定位→最小修复 | 只读 |
| 验证 | 全量+回归 | 修复用例+回归 | 可加引用溯源 |
| 交付 | diff+变更说明 | diff+根因+回归 | 结构化回答+引用 |
| 修正循环 | 常规 | 关键（错误分类路由） | 无 |

## 4. 技术挑战与应对方向

下表将卷一「能力边界」中的实证短板映射为具体对策，并与设计原则/机制对齐。

| # | 挑战 | 典型表现 | 应对方向 | 关联机制 |
| --- | --- | --- | --- | --- |
| **C1** | 长任务目标漂移 | 数十次工具调用后偏离原始需求 | TaskState 外置并每轮刷新原始目标/约束；checkpoints 检查点恢复；压缩/重启不丢失 | P6, ADR-5 |
| **C2** | 浅层修复 | 硬编码/跳过检查让任务"看起来"完成，回归率高 | 验收标准可执行化；每次修改后重验强制（跑测试）；失败历史记录；回归率指标监控 | P3, 5.3 |
| **C3** | 算法级错误 | 实现正确但思路错误，反馈循环难自愈 | 错误分类路由：语法/运行时→迭代修复；答案错/超时→回溯规划层；预算耗尽升级人工 | 范式四, ADR-1 |
| **C4** | 安全边界 | 自生成代码执行、破坏性操作风险 | 沙箱化执行；权限分级；危险命令拦截；破坏性操作显式确认 | P5, ADR-3, Phase 2 |
| **C5** | 成本与缓存效率 | token 随会话线性增长 | prompt cache 透传；compaction 压缩；小上下文混合检索；模型路由（推理/快速） | ADR-6, P4 |
| **C6** | 多文件一致性 | 跨文件修改/重构时接口与调用失真 | Repo Map + 依赖图扩展；符号索引；变更影响面分析 | ADR-4 |
| **C7** | 需求歧义 | 产品级模糊决策无法自主裁决 | 澄清问题生成前置；AskUser 交互；验收测试前置确认 | 1.1 边界 |
| **C8** | 评测与回归 | 难以量化自治质量、防止退化 | ISR@k / MIS 评测；回放测试；升级率/Token 效率/回归率监控 | 5.3, Phase 4 |

**优先级建议**：C1/C2/C4 关系数据安全与基础可信度，应在 Phase 2 内闭环；C3/C6 影响复杂任务上限，随 Phase 3–4 演进；C5/C7/C8 为长期工程化投入。

## 5. 技术选型与实施路线图

### 5.1 技术选型

| 组件 | 建议 | 备选/理由 |
| --- | --- | --- |
| **实现语言** | TypeScript（Node.js） | 生态成熟、流式自然；追求分发性能可选 Rust，但初期成本高 |
| **LLM 网关** | 统一抽象层 + 多模型路由 | 推理型(规划/修复)+快速型(生成)；须透传 prompt cache |
| **代码解析** | Tree-sitter | 多语言 AST，符号索引与 AST 感知分块 |
| **向量检索** | 本地嵌入式（LanceDB 级） | 项目级无需独立向量服务 |
| **词法检索** | ripgrep | 事实标准，性能极佳 |
| **沙箱** | Docker（默认）+ 受限子进程（降级） | Win 注意 Docker Desktop；降级需显式隔离 |
| **协议扩展** | MCP 客户端 | 外部工具生态事实标准 |
| **配置格式** | AGENT.md（记忆）+ JSON/YAML（参数） | 模型路由/预算/迭代上限/权限均外置可调 |

### 5.2 实施路线图

- **Phase 1 · MVP 最小可用循环**：单层 Agent Loop + JSONL 日志；工具最小集（read/list/grep/edit/write/run）；全量历史+截断；交付「定位→修改→跑测试→修复」闭环。
- **Phase 2 · 规划与验证体系**：需求解析流水线（意图+澄清+验收）；TaskState 持久化+完成判定；错误分类路由+迭代预算+升级；权限分级与危险命令拦截（覆盖 C1/C2/C4）。
- **Phase 3 · 上下文工程**：混合检索+Repo Map；ContextBudget 装配+Compaction；长期记忆双轨（AGENT.md+动态记忆）（覆盖 C5/C6）。
- **Phase 4 · 工程化与扩展**：沙箱强化（Docker/限额/网络白名单）；MCP+子任务派生；评测体系（ISR@k/MIS+回放）；会话恢复+检查点（覆盖 C3/C8）。

### 5.3 度量指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **ISR@k** | k 轮内任意一次通过验收的比例 | 核心质量指标 |
| **MIS** | 中位解决轮数 | 控成本与体验 |
| **升级率** | 升级人工的比例 | 衡量自治边界 |
| **Token 效率** | 单位任务 token 消耗 | 随版本持续下降 |
| **回归率** | 声称完成但未通过验收的比例 | 越低越好（浅层修复治理，对应 C2） |
