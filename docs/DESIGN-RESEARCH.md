# AI Coding Agent 设计文档 · 卷一：调研与决策依据

> 项目代号：mod-agent ｜ 版本：v1.0（设计阶段）
> 本卷聚焦「为什么这么做」：目标定位、设计原则、术语，以及对 Claude Code / Codex CLI / Cursor / Devin / OpenHands / SWE-agent 的调研结论。系统设计见卷二。

---

## 1. 目标定位与边界

构建一个**理解自然语言需求、自动生成与修改代码的 AI Coding Agent**，核心能力：

1. **需求理解**：将模糊描述解析为结构化、可验证的开发任务；
2. **代码生成**：greenfield 与 brownfield 双场景高质量产出；
3. **代码修改**：定位、编辑、重构，以可审查 diff 呈现；
4. **环境交互**：读写文件、执行命令、跑测试、检索代码库；
5. **自我修正**：基于编译/测试/lint 反馈迭代修复至验收通过。

**边界**：人类监督下的委托执行系统，而非完全自主的「AI 软件工程师」。人类负责需求决策与最终审查，Agent 负责探索、实现、验证与迭代。

## 2. 设计原则

调研表明，拉开 Coding Agent 差距的不是模型本身，而是 **Agent Runtime（运行时）** 设计。本设计遵循以下原则：

| 原则 | 说明 | 依据 |
| --- | --- | --- |
| **P1 单循环优先** | 单 Agent ReAct 循环为核心，不引入复杂多 Agent 编排；确有需要时子任务派生做受控扩展 | Claude Code / Codex 均为单 Agent 事件循环 |
| **P2 接口即能力(ACI)** | 工具输入输出契约的重要性不亚于模型能力；工具返回须为模型易读、无歧义的结构化文本 | SWE-agent：仅靠改进 ACI 将解决率从 ~2% 提升至 12.5% |
| **P3 验证驱动** | 「生成」廉价、「验证」昂贵且关键；任何修改须经执行验证，以可执行测试为核心反馈信号 | 执行反馈研究：语法/运行时错误可迭代修复，算法级错误需回溯规划 |
| **P4 上下文是缓存** | 分层存储、按需加载（progressive disclosure）、自动压缩（compaction）、记忆外置 | Cursor RAG / Claude Code compaction / 四层记忆模型 |
| **P5 安全默认** | 文件写入、命令执行、网络访问默认隔离与授权；破坏性操作须显式确认 | 所有生产级系统共同设计 |
| **P6 状态外置可恢复** | 目标/约束/失败历史持久化为 Task State，长任务可从任意检查点恢复 | 长程任务失败模式研究（goal drift / shallow repair） |

## 3. 术语表

| 术语 | 定义 |
| --- | --- |
| **Agent Loop** | 核心循环：组装上下文 → 调用 LLM → 解析输出 → 执行工具 → 回填观察 → 判断是否完成 |
| **ReAct** | Reason + Act：每轮交替输出推理过程与工具调用 |
| **ACI** | Agent-Computer Interface，Agent 与工具/环境的交互契约 |
| **Tool Use** | LLM 以结构化 JSON 发起工具调用，运行时代为执行并返回结果 |
| **Compaction** | 上下文压缩：将历史对话摘要化释放窗口空间 |
| **Repo Map** | 代码库结构地图（目录树、符号索引、依赖图） |
| **Goal Drift** | 目标漂移：长任务中 Agent 偏离原始需求 |
| **Shallow Repair** | 浅层修复：借硬编码/跳过检查让任务「看起来」完成 |
| **SWE-bench** | 基于 2294 个真实 GitHub issue 的编码基准；SOTA 从 2023.10 的 1.96% 升至 2026 春的 ~78% |

## 4. 领域调研综述

### 4.1 主流实现对比

| 维度 | Claude Code | Codex CLI | Cursor | Devin | OpenHands | SWE-agent |
| --- | --- | --- | --- | --- | --- | --- |
| **形态** | CLI/SDK 本地 | CLI 本地(Rust) | IDE 内嵌 | 云端托管 | 开源自部署 | 研究框架 |
| **架构哲学** | 主动规划 | 极简 Shell | 检索优先 | 端到端黑盒 | 模块化分层 | 最小 Loop |
| **上下文策略** | 大窗口+主动扫描+压缩 | 最小上下文按需拉取 | 小窗口+向量索引 | 不公开 | 会话压缩+缓存 | 逐轮文件视图 |
| **工具体系** | 结构化专用工具+MCP | shell+apply_patch | IDE 原生 | 浏览器/终端/编辑器 | 可插拔+Docker | 自定义 ACI |
| **记忆机制** | CLAUDE.md 双轨+压缩 | AGENTS.md | 向量+.cursorrules | 内置记忆 | Memory+压缩 | 无持久记忆 |
| **适用场景** | 大型重构/跨系统自动化 | 精准修改/迁移 | 日常 IDE 开发 | 快速 MVP | 团队定制 | 算法研究/评测 |

**核心结论**：
1. 各系统底层都是「单 Agent 事件循环」，差异仅在上下文获取策略（主动扫描 vs 按需拉取）与工具粒度（专用 vs 通用 shell）；
2. 消息历史刻意保持扁平，以匹配 LLM 无状态回放模型并最大化 prompt cache 命中；
3. 性能跃迁来自脚手架（ACI、上下文工程）而非单纯模型升级。

### 4.2 核心架构范式

**范式一 · Agent Loop（运行时核心）**
```
while not done:
    context = assemble_context(task_state, history, memory, repo_map)
    output  = llm(context)              # 文本 或 工具调用
    if output is tool_call:
        result = execute(tool_call)     # 隔离执行 + 权限检查
        history.append(tool_call, result)
    else:
        done = judge_completion(output)
```
新一代升级为分层循环：主循环（任务级，支持中断/恢复/并行子任务）、子循环（步骤级）、工具循环（如「改文件→跑测试→修复」）。

**范式二 · 五层 Runtime**
```
┌─────────────────────────────────────────┐
│  Agent Loop（循环调度：ReAct 分层循环）      │
├─────────────────────────────────────────┤
│  Planner（规划：任务分解 / 路线选择）        │
├─────────────────────────────────────────┤
│  Executor（执行：工具调用 / 沙箱运行）       │
├─────────────────────────────────────────┤
│  State Store（消息日志 / Task State）      │
├─────────────────────────────────────────┤
│  Environment（文件系统 / Shell / 网络）    │
└─────────────────────────────────────────┘
```
Claude Code、Codex、Cursor、OpenHands 均向此五层架构收敛。

**范式三 · 四层记忆模型**

| 层 | 内容 | 生命周期 | 载体 |
| --- | --- | --- | --- |
| L1 上下文内 | 当前请求 token（打开的文件、最近工具结果） | 单次请求 | 消息列表 |
| L2 会话缓存 | 序列化对话与草稿状态 | 会话期 | 本地 JSON / 会话文件 |
| L3 结构化存储 | 嵌入索引、repo map、符号索引 | 项目期 | 向量库 / 索引文件 |
| L4 参数化记忆 | 预训练通用编程知识 | 静态 | 模型本身 |

典型病症：幻觉 import 路径 = L3 缺失时 L4 补位；遗忘早期约束 = L1 淘汰后无 L2/L3 兜底。

**范式四 · 执行反馈闭环**
```
生成 → 沙箱执行 → 结构化错误捕获 → 反馈注入 → 修正 → 重跑 →（通过 | 预算耗尽升级人工）
```
实证结论（Zhang & Kothari）：推理型模型更善用反馈；语法/运行时错误高度可迭代，错误答案/超时须回溯规划而非局部修补；以 ISR@k（k 轮内任意通过率）、MIS（中位解决轮数）衡量。

### 4.3 能力边界（2025–2026 实证）

| 维度 | 当前边界 |
| --- | --- |
| 单点代码生成 | 单函数/文件已成熟（HumanEval 饱和），瓶颈在多文件一致性 |
| 真实 issue 修复 | SWE-bench Verified SOTA ~78%，约 1/4 仍无法自主解决 |
| 长程任务 | 数十次工具调用后目标漂移，需外置 Task State 对抗 |
| 算法级错误 | 反馈循环难自动发现「思路错误」，需回溯规划或人工介入 |
| 需求理解 | 擅长明确需求转代码；产品级模糊决策须向人类澄清 |
| 安全/成本 | 自生成代码须沙箱化；成本随会话线性增长，缓存与压缩是必要工程 |

### 4.4 典型应用场景

功能开发 · Bug 修复 · 大型重构 · 外科手术式修改（迁移/签名替换）· 代码库问答 · 测试补全与修复 · 自动化流水线（CI 自动修复、依赖升级）。
