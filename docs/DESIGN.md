## 1. 引言

### 1.1 目标与定位

本系统旨在实现一个**能够理解自然语言需求并自动生成、修改代码的 AI Coding Agent**。其核心能力包括：

1. **需求理解**：将模糊的自然语言描述解析为结构化、可验证的开发任务；
2. **代码生成**：在新项目（greenfield）与既有代码库（brownfield）两种场景下生成高质量代码；
3. **代码修改**：对既有代码进行定位、编辑、重构，并以可审查的 diff 形式呈现变更；
4. **环境交互**：通过工具调用读写文件、执行命令、运行测试、检索代码库；
5. **自我修正**：基于执行反馈（编译错误、测试失败、lint 告警）迭代修复，直至满足验收标准。

**定位边界**：本系统是一个「 delegated execution under human supervision（人类监督下的委托执行）」系统，而非完全自主的"AI 软件工程师"。人类负责需求决策与最终审查，Agent 负责探索、实现、验证与迭代。

### 1.2 设计原则

调研显示，真正拉开 Coding Agent 差距的不是模型本身，而是 **Agent Runtime（运行时系统）** 的设计。本设计遵循以下从调研中提炼的原则：

| 原则 | 说明 | 来源依据 |
|---|---|---|
| **P1 单循环优先** | 以单 Agent 的 ReAct 循环（思考→工具→观察→重复）为核心，不引入复杂多 Agent 编排；确有需要时通过「子任务派生」做受控扩展 | Claude Code / Codex 均为单 Agent 事件循环；多 Agent 系统在复杂度收益上并不稳定 |
| **P2 接口即能力（ACI）** | Agent-Computer Interface（工具的输入输出契约设计）的重要性不亚于模型能力；工具返回信息必须是模型易读、无歧义的结构化文本 | SWE-agent：同一模型仅靠改进 ACI 即将解决率从 ~2% 提升至 12.5% |
| **P3 验证驱动** | 「生成」廉价，「验证」昂贵且关键。任何修改必须经过执行验证才算完成；以可执行测试作为核心反馈信号 | 执行反馈研究表明：语法/运行时错误可迭代修复，算法级错误需回溯规划 |
| **P4 上下文是缓存** | 上下文管理本质是缓存管理：分层存储、按需加载（progressive disclosure）、自动压缩（compaction）、持久记忆外置 | Cursor RAG / Claude Code compaction / 四层记忆模型 |
| **P5 安全默认** | 文件写入、命令执行、网络访问默认隔离与需授权；破坏性操作（删除、覆盖、force push）必须显式确认 | 所有生产级系统的共同设计 |
| **P6 状态外置可恢复** | 任务目标、约束、失败历史持久化为 Task State，长任务可从任意检查点恢复，对抗目标漂移 | 长程任务失败模式研究（goal drift / shallow repair） |

### 1.3 术语表

| 术语 | 定义 |
|---|---|
| **Agent Loop** | 核心运行循环：组装上下文 → 调用 LLM → 解析输出 → 执行工具 → 回填观察结果 → 判断是否完成 |
| **ReAct** | Reason + Act 范式：模型在每轮交替输出推理过程与工具调用 |
| **ACI** | Agent-Computer Interface，Agent 与工具/环境交互的接口契约 |
| **Tool Use / Function Calling** | LLM 以结构化 JSON 形式发起工具调用，由运行时代为执行并返回结果 |
| **Compaction** | 上下文压缩：将历史对话摘要化以释放上下文窗口空间 |
| **Repo Map** | 代码库结构地图（目录树、符号索引、依赖图），作为代码库的"目录页" |
| **Goal Drift** | 目标漂移：长任务中 Agent 偏离原始需求的现象 |
| **Shallow Repair** | 浅层修复：Agent 通过硬编码、跳过检查等方式让任务"看起来"完成 |
| **SWE-bench** | 基于 2294 个真实 GitHub issue 的 Agent 编码能力基准；SOTA 从 2023.10 的 1.96% 升至 2026 春的 ~78% |

## 2. 功能清单

按优先级分级：**P0**（MVP 必备，无此则无法形成闭环）、**P1**（核心体验，显著提升完成率与可用性）、**P2**（增强能力，差异化与工程化）。

### 2.1 需求理解与规划

| 优先级 | 功能 | 描述 |
|---|---|---|
| P0 | 自然语言任务输入 | 接收用户以自然语言描述的开发需求，支持多行与代码片段 |
| P0 | 意图分类 | 自动识别任务类型：feature（新功能）/ bugfix（缺陷修复）/ refactor（重构）/ question（代码库问答）/ surgical-edit（外科手术式修改） |
| P0 | 歧义检测与澄清 | 识别无法自主裁决的产品级模糊决策点，生成澄清问题交用户确认；答案固化为验收标准 |
| P0 | 约束提取 | 提取硬约束与隐含期望（不改依赖、兼容版本、性能要求、列顺序等） |
| P1 | 验收标准生成 | 将需求转写为可验证的验收条目，尽可能直接转为可执行测试（测试先行） |
| P1 | 分步计划生成 | 输出可验证的工作单元步骤（改动 + 对应验证方式），支持用户确认 / 修订 |
| P1 | 计划修订追踪 | 执行中修订计划必须记录原因，对抗目标漂移（goal drift） |

## 3. 领域调研综述

### 3.1 主流实现对比

| 维度 | Claude Code | Codex CLI | Cursor | Devin | OpenHands | SWE-agent |
|---|---|---|---|---|---|---|
| **形态** | CLI / SDK，本地运行 | CLI，本地运行（Rust） | IDE 内嵌 | 云端全托管 | 开源框架（自部署） | 学术研究框架 |
| **架构哲学** | 主动规划型（proactive planner） | 极简 Shell 型（shell-first surgeon） | 检索优先（RAG + 小上下文） | 端到端黑盒 | 模块化分层 | 最小 Agent Loop |
| **上下文策略** | 大窗口（200K）+ 结构化工具主动扫描 + 自动压缩（~92% 触发 compaction） | 最小上下文，按需 `cat`/`grep` 拉取，AGENTS.md 持久指令 | 默认 ~20K 小窗口，AST 分块 + 向量索引（LanceDB）按需检索 | 不公开 | 会话内压缩 + 摘要 + 工具结果缓存 | 逐轮文件视图，无全局索引 |
| **工具体系** | 结构化专用工具（View/Glob/Grep/Edit/Bash）+ MCP 生态 | 通用 shell + apply_patch 统一 diff 编辑器 | IDE 原生能力（@codebase 语义搜索、定义跳转） | 内置浏览器、终端、编辑器三件套 | 可插拔 Action Space（bash/编辑/浏览）+ Docker 沙箱 | 自定义 ACI 命令集（导航/编辑/测试） |
| **记忆机制** | CLAUDE.md 双轨记忆（全局偏好 + 项目规范）+ 压缩摘要块 | AGENTS.md 持久指令 | 向量索引 + .cursorrules | 内置记忆系统（可从历史任务学习） | Memory 模块 + 会话压缩 | 无持久记忆（研究导向） |
| **可定制性** | 高（SDK / MCP 扩展） | 高（开源 Rust） | 中（产品化配置） | 低（黑盒托管） | 极高（全开源模块化） | 高（学术实验用） |
| **适用场景** | 大型风格敏感重构、跨系统多工具自动化 | 外科手术式精准修改、框架迁移 | 日常 IDE 内交互式开发 | 快速 MVP、非技术用户 | 自建基础设施的团队定制 | 算法研究、评测 |

**关键观察**：

1. **两大流派的共同内核**：无论 Claude Code 还是 Codex，底层都是同一个东西——「单 Agent 事件循环：收集上下文 → 执行动作（工具）→ 观察结果 → 决定下一步 → 重复」。没有 Swarm、没有隐藏的图编排。差异只在于**上下文获取策略**（主动扫描 vs 按需拉取）与**工具粒度**（结构化专用工具 vs 通用 shell）。
2. **消息历史刻意保持扁平**：一条线性的消息与工具调用日志。简单性是有意为之的设计决策——这保证了与 LLM API 无状态回放模型的一致性，也最大化了 provider 端 prompt cache 的命中率。
3. **性能跃迁来自脚手架而非模型**：SWE-bench 从 1.96% 到 78% 的提升中，SWE-agent 的 ACI 设计、Claude Code 的上下文工程贡献了与模型升级同等重要的份额。

### 3.2 核心架构范式提炼

#### 范式一：Agent Loop（运行时核心）

```
while not done:
    context = assemble_context(task_state, history, memory, repo_map)
    output  = llm(context)                    # 文本 或 工具调用
    if output is tool_call:
        result = execute(tool_call)            # 隔离执行 + 权限检查
        history.append(tool_call, result)      # 观察结果回填
    else:
        done = judge_completion(output)        # 完成判定
```

新一代运行时已将此循环升级为分层循环（Hierarchical Loop）：

- **主循环**（任务级）：管理整个任务生命周期，支持中断/恢复/并行子任务；
- **子循环**（步骤级）：每个规划步骤一个循环；
- **工具循环**（执行级）：如「修改文件 → 运行测试 → 修复」的微循环。

#### 范式二：Agent Runtime 五层架构

```
┌─────────────────────────────────────────┐
│  Agent Loop（循环调度：ReAct 分层循环）      │
├─────────────────────────────────────────┤
│  Planner（规划：任务分解 / 路线选择）        │
├─────────────────────────────────────────┤
│  Executor（执行：工具调用 / 沙箱运行）       │
├─────────────────────────────────────────┤
│  State Store（状态：消息日志 / Task State）  │
├─────────────────────────────────────────┤
│  Environment（环境：文件系统 / Shell / 网络）│
└─────────────────────────────────────────┘
```

Claude Code、Codex、Cursor、OpenHands 本质上都在向这个五层架构收敛。

#### 范式三：四层记忆模型

| 层 | 内容 | 生命周期 | 实现载体 |
|---|---|---|---|
| L1 上下文内 | 当前 API 调用中的 token（打开的文件、最近的工具结果） | 单次请求 | 消息列表 |
| L2 会话缓存 | 序列化的对话与草稿状态 | 会话期内 | 本地 JSON / 会话文件 |
| L3 结构化存储 | 代码库嵌入索引、repo map、符号索引 | 项目生命周期 | 向量库 / 索引文件 |
| L4 参数化记忆 | 模型预训练权重中的通用编程知识 | 静态 | 模型本身 |

**典型病症映射**：幻觉的 import 路径 = L3 检索缺失时 L4 补位；遗忘早期约束 = L1 淘汰后无 L2/L3 兜底。

#### 范式四：执行反馈闭环

```
生成 → 沙箱执行 → 结构化错误捕获 → 反馈注入 → 修正 → 重跑 →（通过 | 预算耗尽升级人工）
```

实证研究（Zhang & Kothari, *Unlocking LLM Code Correction with Iterative Feedback Loops*）的核心结论：

- 执行反馈显著改善困难问题的解决率，且**推理型模型比非推理型模型更能利用反馈循环**；
- **语法错误、运行时错误**：高度可迭代修复；**错误答案、超时**：常需更换底层算法而非局部修补——此时应回溯到规划层；
- 有效指标：ISR@k（k 轮内任意一次通过率）、MIS（中位解决轮数）——"十轮后终于对"与"两轮就对"是不同的产品。

### 3.3 能力边界

| 能力维度 | 当前边界（2025–2026 实证） |
|---|---|
| **单点代码生成** | 单函数/单文件生成已高度成熟（HumanEval 饱和）；瓶颈在多文件一致性 |
| **真实 issue 修复** | SWE-bench Verified SOTA ~78%，仍有约 1/4 的真实 issue 无法自主解决 |
| **长程任务** | 数十次工具调用后出现目标漂移；需要外置 Task State 对抗 |
| **算法级错误修复** | 反馈循环只能修复"实现错误"，难以自动发现"思路错误"，需回溯规划或人工介入 |
| **需求理解** | 擅长将明确需求转为代码；对**产品级模糊决策**（如"删除账户时订阅如何处理"）无法自主裁决，需向人类澄清 |
| **安全边界** | 自生成代码的执行必须沙箱化；任意代码执行是最高风险面 |
| **成本** | 对话无状态回放模型导致成本随会话长度线性增长；token 缓存与压缩是必要工程 |

### 3.4 典型应用场景

1. **功能开发（Feature Development）**："给用户服务加一个账户注销接口"——涉及多文件修改、测试编写、验收标准确认；
2. **Bug 修复（Issue Resolution）**：输入 issue 描述 + 复现路径，Agent 定位→修复→回归测试；
3. **重构（Refactoring）**：风格敏感的大型重构（如 MVC 化改造），需要全局代码库理解；
4. **外科手术式修改（Surgical Edits）**：框架迁移、API 签名替换等精确局部变更；
5. **代码库问答与探索（Codebase Q&A）**：只读场景，"这个支付模块的调用链是什么"；
6. **测试补全与修复**：基于现有实现补齐回归测试，或修复 CI 失败；
7. **自动化流水线**：CI 失败自动修复、依赖升级等无人值守场景（需要更强的安全边界）。

### 4.2 架构决策记录（ADR 摘要）

| # | 决策 | 理由 |
|---|---|---|
| ADR-1 | **单 Agent 主循环 + 受控子任务派生**，不做对等 Multi-Agent 编排 | 主流验证：单循环可解释、可恢复、成本可控；Claude Code / Codex 均如此。子任务（如独立代码库探索）可作为轻量子 Agent 运行并回传摘要 |
| ADR-2 | **扁平消息日志**作为唯一事实源（Source of Truth） | 与 LLM 无状态回放模型天然一致；最大化 prompt cache 命中；简化调试与回放 |
| ADR-3 | **结构化专用工具为主、通用 Shell 为辅** | 结构化工具（读文件/grep/受控编辑）返回模型友好的确定性输出；Shell 保留给构建/测试等必须场景。这是 Claude Code 与 Codex 两条路线的折中 |
| ADR-4 | **混合检索（词法 + 符号 + 语义 + 依赖图扩展）**，不单纯依赖向量 RAG | 编码任务大量锚定在精确标识符（函数名/错误串）上，纯语义检索召回不足；Cursor 的实践验证了混合路线 |
| ADR-5 | **Task State 外置持久化**（TASK_STATE 文件） | 对抗长任务目标漂移：每轮循环后显式刷新「原始目标 / 已完成 / 失败历史 / 验收标准」，压缩或重启后不丢失 |
| ADR-6 | **LLM 网关统一封装**（多模型路由、缓存、限流、重试） | 推理型模型用于规划与疑难修复、快速模型用于常规生成，是成本/质量的关键杠杆；同时隔离 provider 差异 |

### 4.3 核心数据模型

```typescript
// 消息（扁平日志的最小单元）
interface Message {
  role: "system" | "user" | "assistant" | "tool_result";
  content: string | ContentBlock[];   // 支持 text / image / tool_call
  tool_call_id?: string;              // 关联的工具调用
  token_count: number;                // 用于预算管理
  created_at: string;                 // ISO 时间戳
}

// 工具调用
interface ToolCall {
  id: string;
  name: string;                  // 如 "read_file" / "edit_file" / "run_command"
  arguments: Record<string, unknown>;  // Zod 校验后的参数
  requires_approval: boolean;    // 是否需要用户授权
}

// 任务状态（外置持久化，对抗目标漂移）
interface TaskState {
  task_id: string;
  original_request: string;          // 原始需求，永不被改写
  clarified_requirements: string[];  // 澄清后的明确需求
  constraints: string[];             // 硬约束（不许改依赖、不许动生产数据）
  plan: PlanStep[];                  // 当前计划（可被修订）
  acceptance_criteria: string[];     // 验收标准（尽可能转成可执行测试）
  attempted_fixes: FixRecord[];      // 失败修复记录（含测试输出）
  status: "planning" | "executing" | "verifying" | "done" | "blocked";
  checkpoints: Checkpoint[];         // 检查点（消息日志快照）
}

// 上下文预算（128K 窗口的典型分配，单位：token）
interface ContextBudget {
  system_prompt_and_tools: number;   // 系统提示 + 工具定义（~5_000）
  task_definition: number;           // 任务定义 + Task State 摘要（~2_000）
  recent_history: number;            // 最近对话轮次（~10_000）
  retrieved_code: number;            // 检索到的代码块，占大头（~80_000）
  working_memory: number;            // 当前编辑缓冲、假设、中间发现（~20_000）
  response_buffer: number;           // 模型输出预留（~11_000）
}

## 5. 核心模块设计

### 5.1 需求解析与任务规划模块（Intent Parsing & Planning）

**职责**：将自然语言需求转化为结构化、可验证、可执行的任务计划。

#### 5.1.1 处理流水线

```
自然语言输入
    │
    ▼
[意图分类] 是什么类型的任务？
    │  feature / bugfix / refactor / question / surgical-edit
    ▼
[歧义检测] 识别无法自主裁决的产品级模糊点
    │  ├── 有歧义 → 生成澄清问题，交人类决策（AskUser 交互）
    │  └── 无歧义 ↓
    ▼
[约束提取] 提取硬约束与隐含期望
    │  "不要改依赖" "保持列顺序" "兼容 Python 3.10"
    ▼
[验收标准生成] 将需求转写为可验证的验收条目
    │  尽可能直接转成可执行测试（acceptance tests before code）
    ▼
[代码库勘探] 定位相关文件/模块，生成任务局部 Repo Map
    │
    ▼
[计划生成] 输出分步计划（Plan），交用户确认后进入执行
```

#### 5.1.2 设计要点

1. **规划与执行分离但同循环**：规划是 Agent Loop 中的一个阶段（产出 PlanStep 列表写入 TaskState），而不是独立的常驻组件。执行中允许修订计划，但修订必须记录原因——对抗目标漂移。
2. **澄清问题生成**（关键差异化能力）：模糊需求的典型处理——"删除账户时，活跃订阅是先取消还是阻止删除？唯一所有者能否直接删除？"这类问题必须浮出给用户，**答案要固化为验收测试**，而不是留在聊天记录里。
3. **测试先行**：验收标准在写第一行实现代码之前生成。这是六大反馈循环中"规划循环"的核心——测试没覆盖产品决策，等于没有闭环。
4. **计划粒度**：每步应是一个「可验证的工作单元」（改动 + 对应验证方式），避免"重写整个模块"式的粗粒度步骤。

### 5.2 代码生成与修改模块（Code Generation & Editing）

**职责**：产出新代码与对既有代码的受控修改，以 diff 为核心交付单元。

#### 5.2.1 代码生成

- **输入组装**：任务步骤 + 检索到的相关代码 + 项目规范（来自记忆模块）+ 语言/框架约定；
- **生成策略**：
  - 优先「局部修改」而非「整文件重写」——控制 diff 爆炸半径；
  - 多方案候选（best-of-n）仅用于关键决策点（如架构选型处），常规生成单次出稿以控成本；
- **静态校验前置**：生成后先过语法解析（AST）与 lint，再进入执行验证——把低成本检查放在最前面。

#### 5.2.2 代码编辑（Edit 协议）

受控编辑工具的三种实现路线对比：

| 路线 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 整文件重写 | 早期工具 | 实现简单 | token 浪费、diff 噪音大、易破坏无关代码 |
| 字符串替换（old/new 对） | Claude Code / Aider | 精确、diff 干净 | 匹配失败需重读文件；模型需先读过目标文件 |
| 统一 diff / apply_patch | Codex CLI | 标准化、可审查 | 模型生成的 diff 格式错误率较高，需容错解析 |

**本设计采用**：字符串替换为主（要求编辑前必须先 read 目标文件，工具侧校验 old 串唯一性），apply_patch 为兜底。同时强制：

- **编辑前哈希校验**：edit_file 携带 read 时的文件版本号，文件若已被外部修改则拒绝编辑并要求重读——对抗"陈旧快照"问题（stale snapshot）；
- **失败即停**：工具报错（文件不存在、匹配失败）时不允许模型"自创路径新建重复文件"，必须停下重读——防止级联幻觉（cascading hallucination）。

### 5.3 工具系统与环境交互模块（Tool System & Environment）

**职责**：定义 ACI 契约、调度执行、隔离风险、返回模型友好的结构化结果。

#### 5.3.1 内置工具集（最小充分集）

| 工具 | 说明 | 关键设计（ACI 要点） |
|---|---|---|
| `read_file` | 读取文件（支持行号范围） | 输出带行号前缀；超过 ~4K token 自动截断并提示分段读取 |
| `list_dir` / `glob` | 目录列表 / 模式匹配找文件 | 返回按修改时间排序的相对路径 |
| `grep` | 正则搜索（ripgrep 后端） | 返回文件:行号:匹配行；带上下文行数控制 |
| `edit_file` | 受控字符串替换编辑 | 见 5.2.2 编辑协议 |
| `write_file` | 新建文件 | 需授权；拒绝覆盖已存在文件（用 edit_file） |
| `run_command` | 沙箱内执行 shell | 超时控制、输出截断（保留错误尾部）、退出码显式返回 |
| `run_tests` | 运行测试套件 | 优先于裸 run_command——自动解析测试框架输出为结构化失败列表 |
| `search_codebase` | 混合检索（见 5.4.3） | 融合词法/符号/语义结果，返回去重排序后的代码块 |
| `ask_user` | 向用户提问/请求授权 | 澄清产品决策、危险操作确认 |

**工具输出预算**：所有工具结果强制截断（默认 ~4K token/次）。2000 行测试日志直接塞上下文会一次吃掉 4K+ token——截断策略保留「错误信息尾部 + 摘要头部」。

#### 5.3.2 沙箱与执行环境

```
工具调用 → 权限检查（Security Gate）→ 执行隔离层 → 结果规整 → 回填消息日志
```

- **分级隔离**：
  - 只读工具（read/grep/glob）：低风险，直接执行；
  - 写操作（edit/write）：路径白名单（工作区内）+ 版本校验；
  - 命令执行：默认在沙箱（Docker 容器 / 受限子进程）中运行，网络默认禁用、内存与 CPU 限额、超时强杀；
- **破坏性命令拦截**：`rm -rf`、`git push --force`、`git reset --hard` 等模式命中时升级为人工确认；
- **确定性优先**：同一命令重跑结果应可复现（禁用随机性注入、固定时区/locale）。

#### 5.3.3 MCP 扩展

实现 MCP（Model Context Protocol）客户端，支持接入外部工具服务器（数据库、issue 跟踪、浏览器自动化等）。MCP 的关键价值：**外部数据以指针形式存在于上下文**（如一个小 ID），仅在需要计算/查询时才展开——保持上下文窗口干净。

### 5.4 上下文与记忆管理模块（Context & Memory Management)

**职责**：在有限的上下文窗口内，让模型每轮都看到「完成任务所必需的最小充分信息」。

#### 5.4.1 四层记忆落地

| 层 | 本设计实现 |
|---|---|
| L1 上下文内 | Agent Loop 每轮组装的消息列表（受 ContextBudget 约束） |
| L2 会话缓存 | 会话文件（JSONL 持久化消息日志 + TaskState），支持会话恢复 |
| L3 项目结构化存储 | Repo Map + 向量索引（AST 感知分块）+ 符号索引（Tree-sitter） |
| L4 参数化 | 由 LLM 网关选择的底层模型承载 |

#### 5.4.2 上下文组装器（Context Assembler）

每轮循环按预算装配上下文，优先级从高到低：

```
系统提示 + 工具定义（不变前缀，最大化 prompt cache 命中）
  → TaskState（原始需求 / 约束 / 当前计划 / 验收标准）   ← 每轮刷新
  → 相关代码块（检索结果，占预算大头 ~60%）
  → 最近 N 轮完整对话 + 工具结果
  → 长期记忆注入（项目规范 memory 文件）
```

**关键规则**：
- **前缀不变性**：已发送的消息内容永不回头修改——这是 provider 端 token 缓存（cached input 价格约为常规 input 的 10%）生效的前提，是架构级约束；
- **渐进式披露**（progressive disclosure）：初始只给项目骨架（repo map 摘要），需要数据库 schema 时才调工具读具体文件——不做"以防万一"的全量预载。

#### 5.4.3 混合检索（Hybrid Retrieval）

```
query → ① 词法检索（ripgrep：精确标识符/错误串）
      → ② 符号检索（AST 索引：函数/类定义跳转）
      → ③ 语义检索（代码嵌入向量 Top-K）
      → 融合去重排序
      → ④ 依赖图一跳扩展（callers/callees/importers）
      → 按 token 预算裁剪 → 注入上下文
```

- **AST 感知分块**：按函数/类边界切分而非固定字符窗口，保证检索粒度是完整的语义单元；
- **增量索引**：文件变更时只重建变更文件的索引（参考 Cursor 的周期性自动重索引）；
- **仓库规模路由**：<100K token 小仓库直接全量加载相关文件；大仓库走混合检索 + 短会话。

#### 5.4.4 上下文压缩（Compaction）

- **触发条件**：上下文使用率达 ~90%（预留压缩动作自身开销）；
- **压缩流程**：
  1. 将较早的历史轮次摘要化（保留：关键决策、约束确认、失败尝试及其原因）；
  2. TaskState 同步刷新（确保验收标准、未完成步骤显式持久）；
  3. 被压缩掉的工具结果以指针形式保留（需要时可重新执行工具获取）；
- **不可压缩区**：系统提示、原始用户需求、当前计划的活跃步骤、最近 1–2 轮——**必须生存于压缩之外的信息放 TaskState / memory 文件**，这是"约束只在系统提示里才能保证每轮重载"原则的落地。

#### 5.4.5 长期记忆（跨会话）

- 双轨制（借鉴 CLAUDE.md 模式）：
  - **静态记忆**：项目根的 `AGENT.md`——项目约定、构建命令、架构说明，由用户/Agent 共同维护，每次会话启动时注入；
  - **动态记忆**：Agent 在任务中发现的持久事实（"测试必须用 pytest 跑，unittest 会有假通过"）由 Agent 主动写入，带来源与时间戳；
- 记忆写入需谨慎：错误记忆会跨会话污染——写入前验证事实（有测试输出佐证）。

### 5.5 执行反馈与自我修正模块（Execution Feedback & Self-Correction）

**职责**：构建「执行 → 结构化错误 → 反馈注入 → 修正 → 重验」的闭环，并管理迭代预算与升级策略。

#### 5.5.1 反馈闭环

```
              ┌──────────────────────────────────┐
              │                                  │
  修改代码 ──▶ 沙箱执行 ──▶ 结果分类 ──▶ 通过？──▶ 完成
              │              │          │
              │              ▼          │ 未通过
              │        结构化错误        │
              │        (编译/测试/lint)  │
              │              │          │
              │              ▼          ▼
              │        错误定位+根因分析 → 修正策略选择
              │              │
              │    ┌─────────┼──────────┐
              │    ▼         ▼          ▼
              │ 局部修复   回溯规划     停止并升级
              │ (语法/运行时) (算法级错误) (预算耗尽/重复失败)
              └──────────────────────────┘
```

#### 5.5.2 设计要点

1. **错误分类路由**（来自实证研究的关键结论）：
   - 语法 / 风格 / 运行时错误 → 局部修复循环（预期 1–3 轮解决）；
   - 断言失败 / 语义错误 → 先分析是"实现错误"还是"方案错误"，后者回溯到规划层修订计划；
   - 超时 / 性能问题 → 几乎必然是算法问题，直接回溯规划；
2. **重验强制**：每次修复后必须重跑失败的那个具体检查，不允许"看起来改对了"就宣称完成——「edit 本身不构成解决证据」；
3. **迭代预算与重复失败检测**：
   - 每步修复循环上限（如 5 次）；同一错误连续 2 次修复后仍复现 → 判定重复失败，停止迭代；
   - 升级路径：携带「已尝试的修复 + 对应测试输出」交给人类，而不是让 Agent 无限重试；
4. **失败历史记录**：每次失败修复（方法 + 测试输出）记入 TaskState.attempted_fixes——防止压缩后 Agent 忘记"这条路走过"，也防止近期偏差（recency bias：连续失败的对话氛围会诱导模型重复错误模式）；
5. **回归测试固化**：执行中发现的每个 bug 修复，都要求沉淀一个「先验证对旧实现失败、再验证对新实现通过」的回归测试——把会话内的教训固化为仓库资产。

### 5.6 安全与权限控制（Security & Permission）

横切于所有模块：

| 控制面 | 机制 |
|---|---|
| **操作分级** | 只读（免授权）/ 写入（白名单路径）/ 命令执行（沙箱）/ 破坏性（人工确认）|
| **路径边界** | 工作区根目录为界；越界读写（如系统目录、用户主目录敏感位置）一律拒绝 |
| **命令静态审查** | 命令模式库拦截高危操作；管道/重定向解构后逐段审查 |
| **网络隔离** | 沙箱内默认禁网；确需联网（拉依赖）时按域名白名单放行 |
| **审计日志** | 全量工具调用与参数落盘（JSONL），支持事后回放与归因 |
| **密钥防护** | 环境变量/配置文件中的密钥在进入上下文前脱敏 |
| **自生成代码执行** | 一律沙箱 + 资源限额——这是最高风险面，绝无例外 |

## 7. 技术挑战与应对方向

| # | 挑战 | 表现 | 应对方向 |
|---|---|---|---|
| C1 | **目标漂移（Goal Drift）** | 数十次工具调用后偏离原始需求；"重构+补回归测试"变成无关的依赖清理 | ① TaskState 每轮显式注入原始需求与约束；② 计划修订必须记录原因；③ 完成判定严格对照验收标准而非 Agent 自述 |
| C2 | **浅层修复（Shallow Repair）** | 捕获异常后硬编码返回值、注释掉失败检查让运行"看起来"通过 | ① 重验强制（修复后必须重跑原失败检查）；② 检查 diff 中的可疑模式（跳过测试、吞异常）；③ 验收测试断言最终状态而非仅返回值 |
| C3 | **上下文溢出与静默截断** | 旧轮次被无提示丢弃，早期约束消失，模型不会自报丢失 | ① 主动 compaction（90% 阈值）而非被动截断；② 硬约束只放系统提示/TaskState（每轮必重载）；③ 工具结果强制截断预算 |
| C4 | **幻觉（API/路径/依赖）** | 引入不存在的包、编造类名——检索缺失时参数化记忆"补位" | ① 混合检索优先命中精确标识符；② 编译器/linter 错误作为工具结果回注；③ 编辑前强制重读文件（哈希校验） |
| C5 | **级联幻觉** | edit 失败 → 模型自创新路径写重复文件 → 漂移加剧 | 工具错误时熔断：失败即停、禁止自创路径、强制重读后重试 |
| C6 | **无限工具循环** | 反复用改写过的 query 重复 search | 最大迭代护栏（每轮 ~10 次工具调用上限）；重复检测（相似调用指纹去重）；预算耗尽升级人工 |
| C7 | **算法级错误不可局部修复** | 反馈循环只能移动括号，不能换算法 | 错误分类路由：断言/超时类失败回溯规划层，而非继续局部修补 |
| C8 | **陈旧文件快照** | 基于旧版本读取结果编辑用户已手动修改的文件 | read 时记录文件版本（hash/mtime），edit 时校验，不一致则拒绝并要求重读 |
| C9 | **近期偏差（Recency Bias）** | 连续失败轮次主导对话"氛围"，模型重复自身错误模式 | 失败历史结构化记录（而非以原始失败文本留存）；必要时"干净重启"：基于 TaskState 重建精简上下文 |
| C10 | **成本随会话线性增长** | 无状态回放模型：每轮重发全部历史，长会话昂贵 | ① 前缀不变性保 prompt cache；② 主动 compaction；③ 子任务派生用独立短上下文，只回传摘要 |
| C11 | **自生成代码执行风险** | 模型生成的代码不可信，任意执行即 RCE | 绝对沙箱（容器隔离 + 资源限额 + 禁网默认）+ 审计日志，无例外 |
| C12 | **评测与回归** | Agent 行为对 prompt/模型版本敏感，改动无回归手段 | ① 建立任务级评测集（feature/bugfix/refactor 各若干）记录 ISR@k 与 MIS；② 端到端回放测试（固定消息日志重放断言工具序列）；③ 模型升级走灰度 |

├── sessions/                      # 会话日志（JSONL）+ TaskState
└── AGENT.md                       # 项目级记忆文件
```

### 8.2 实施路线图

**Phase 1 — 最小可用循环（MVP）**
- Agent Loop（单层循环）+ 消息日志（JSONL）
- 工具最小集：read_file / list_dir / grep / edit_file / write_file / run_command
- 简单上下文组装（全量历史 + 截断）
- 交付物：能在小型仓库完成"定位→修改→跑测试→修复"闭环

**Phase 2 — 规划与验证体系**
- 需求解析流水线（意图分类 + 澄清问题 + 验收标准）
- TaskState 持久化 + 完成判定
- 错误分类路由 + 迭代预算 + 升级机制
- 权限分级与危险命令拦截

**Phase 3 — 上下文工程**
- 混合检索（词法 + 符号 + 语义）+ Repo Map
- ContextBudget 预算装配 + Compaction 压缩
- 长期记忆双轨制（AGENT.md + 动态记忆）

**Phase 4 — 工程化与扩展**
- 沙箱强化（Docker 隔离、资源限额、网络白名单）
- MCP 客户端 + 子任务派生
- 评测体系（ISR@k / MIS 指标 + 回放测试）
- 会话恢复 + 检查点 + 干净重启

### 8.3 度量指标

| 指标 | 定义 | 目标 |
|---|---|---|
| ISR@k | 任务在 k 轮迭代内任意一次通过验收的比例 | 核心质量指标 |
| MIS | 中位解决轮数 | 控制成本与体验 |
| 升级率 | 任务被升级给人工的比例 | 衡量自治边界 |
| Token 效率 | 完成单位任务消耗的 token 数 | 随版本持续下降 |
| 回归率 | Agent 声称完成但实际未通过验收的比例 | 越低越好，衡量浅层修复治理效果 |
